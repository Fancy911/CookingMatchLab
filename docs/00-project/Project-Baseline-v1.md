# 《料理消消研究所》立项基线 v0.1

> 日期：2026-07-21  
> 当前状态：G0 已确认通过；正在进行 G1-A 视觉方向选择，尚未开发核心玩法  
> 目标平台：TapTap 中国大陆，Android 优先  
> 基准画布：竖屏 390×844  
> 项目口号（工作版）：**连一连真下锅，三次投料开新菜。**

---

## 0. 立项结论

### 0.1 是否值得做

**值得，维持 S 级试玩优先级，但必须先验证核心，不应直接扩成完整游戏。**

它真正有潜力的不是“美食题材三消”，而是：

1. 玩家能看懂每一次消除如何改变锅里的材料；
2. 玩家在开锅前会猜测、期待成品；
3. 新料理揭晓本身就是奖励，而不是关卡结束后附送的一张图片；
4. 食材、锅具、配方和料理图鉴可以长期模块化扩充。

只要第 1～3 条不能成立，就应尽早停止扩内容，而不是靠更多关卡、广告和装修掩盖。

### 0.2 本轮冻结的推荐方案

| 项目 | 推荐结论 |
| --- | --- |
| 消除方式 | 不采用传统交换三消；采用 **7×7 同类食材连线采集** |
| 单锅结构 | 每锅默认 3 次投料，可提前开火；临时槽位提供第 4 次投料 |
| 料理生成 | 完全由食材种类、真实数量、比例、锅具与特殊标签确定；同输入必须同结果 |
| 关卡节奏 | 每单 1～2 锅、约 1～3 分钟；首章不做实时倒计时 |
| 稀有度与质量 | 分离：料理有普通/特色/珍稀/传说稀有度；当次烹饪另评 1～3 星；黑暗料理是可叠加的独立标签 |
| 首发商业化 | MVP 不接真实广告 SDK，只用 Mock 验证激励节点并预留完整广告/免广告接口 |
| 技术 | Cocos Creator 3.8.8 LTS + TypeScript，Android 原生构建优先 |
| MVP | 1 个家常厨房、10 种食材、15 道料理、20 个订单、2 个锅具 |

### 0.3 三条项目红线

1. **料理不是装饰。** 玩家若无法根据锅中成分解释为什么生成这道菜，验收不通过。
2. **UI 不是网页。** 不允许用大面积纯色背景、同款圆角卡片、左对齐列表和文字按钮替代游戏场景、美食和动画。
3. **不跨阶段开发。** 当前阶段未签字通过，Codex 不得实现下一阶段的功能、SDK 或内容。

## 1. 产品定义与核心卖点

### 1.1 一句话定位

一款把“消除结果”真实做成料理的竖屏休闲游戏：玩家连线收集食材、观察它们下锅，根据配比和锅具发现新菜，并逐步扩建自己的料理研究所。

### 1.2 四个核心卖点

1. **消什么，就下什么**  
   棋盘上的每颗食材都沿路径飞入锅中，锅边实时显示种类与数量，不做假演出。

2. **三次投料，开锅有悬念**  
   玩家不是照着唯一答案机械消除，而是在订单提示、配方线索与当前棋盘之间做选择。

3. **同样食材，不同锅具做出不同菜**  
   番茄与鸡蛋进炒锅可以成为番茄炒蛋，进汤锅则走向番茄蛋花汤；后续烤箱、烧烤架、甜品台继续扩充。

4. **每一道新菜都是长期收藏目标**  
   普通菜负责熟悉规则，稀有和传说菜由隐藏比例、特殊长连、神秘食材或厨具条件触发；黑暗料理也可收藏，不只是惩罚。

### 1.3 玩家应该产生的三个情绪

- 消除时：**“我想把这些东西丢进去。”**
- 开锅前：**“这一锅到底会是什么？”**
- 揭晓后：**“原来这样能做出来，我还想试一种。”**

### 1.4 明确不做

- 不做剧情驱动、恋爱或大量人物立绘；
- 不做高压经营、体力卡死或长时间等待；
- 不做复杂厨艺模拟和每关多个操作小游戏；
- 不让随机数直接决定最终菜品；
- 不把“研究所”做成冷冰冰的实验室或后台面板。

## 2. 目标用户与 TapTap 市场定位

### 2.1 目标用户

**核心用户**

- 16～35 岁、喜欢竖屏休闲、收集、轻经营和可爱美食内容的玩家；
- 有碎片时间，希望一局 1～3 分钟、无需研究复杂数值；
- 对“解锁图鉴、补齐配方、装饰厨房”有持续动力；
- 预计女性略多，但不以恋爱、人设或少女换装作为唯一吸引点。

**次级用户**

- 喜欢三消/连线但厌倦纯换皮的人；
- 喜欢《可口的披萨》一类“亲手做食物＋配方发现”的玩家；
- 喜欢分享稀有结果、黑暗料理和彩蛋的轻内容玩家。

### 2.2 TapTap 定位

商店标签建议：**休闲 / 消除 / 美食 / 收集 / 单机 / 竖屏 / 可爱**。

推荐对外表述：

> 不是把水果换成食材的普通消除。你连掉的每一份番茄、鸡蛋和香菇都会真的进入锅里，数量、顺序、特殊长连和锅具共同决定最后端上来的料理。

### 2.3 竞品启示

- 《旅行串串》证明 TapTap 上“美食＋竖屏＋收集＋长期扩内容”有成熟受众，但它依赖庞大合成链和长期内容，本项目首版不能照搬其内容规模。
- 《料理之神》已有“消除食材、做菜、装修”的概念，因此仅有题材组合不构成差异化。
- 《料理妈妈 Let's Cook Puzzle》的玩家评价曾直接指出：限时压力让玩家无暇关注料理长什么样，导致料理与消除关系不强。首章因此不采用实时倒计时，必须给开锅和揭晓留出注意力。
- 《可口的披萨》式的长线价值来自配方、装饰与主题活动共同扩展，而不是无限复制普通关卡。

### 2.4 商店名称判断

《料理消消研究所》现阶段可继续使用：含玩法关键词、轻松、容易理解，也给未来中餐/西餐/甜品留出空间。风险是“消消”较泛、品牌辨识度一般。进入资质申请前必须完成：

1. TapTap、应用商店和软著重名检索；
2. 商标与版权风险检索；
3. 备选名 A/B 测试。

搜索结果不能替代正式法律检索。

## 3. 核心玩法详细规则

### 3.1 单局流程

1. 玩家选择订单，看到客人需求和 1～2 条配方提示；
2. 选择已解锁锅具，进入 7×7 食材棋盘；
3. 拖动连接 3 个或以上相邻的同类食材；
4. 松手后食材逐颗飞入锅中，锅边实时累计真实数量；
5. 默认完成 3 次投料后自动开火，也可在 2 次投料后提前开火；
6. 播放 1～3 秒烹饪动画，按确定性规则生成料理；
7. 若订单需要第二道菜，则保留棋盘状态继续下一锅；
8. 结算金币、满意度、研究经验、图鉴与新线索。

### 3.2 棋盘规则

| 规则 | 首版设定 |
| --- | --- |
| 棋盘 | 7×7，首章每局出现 5 类基础食材 |
| 连接方向 | 横、竖、斜 8 邻接 |
| 最短连接 | 3 格 |
| 重复经过 | 不允许重复经过同一格 |
| 数量 | 每个被连接的食材格 = 1 单位入锅量 |
| 补充 | 消除后上方掉落并补齐，不产生自动连锁消除 |
| 单锅投料 | 默认 3 次连接；特殊道具临时增加第 4 次 |
| 开火 | 2 次投料后可提前开火；3 次后自动开火 |
| 失败 | 不是没做出指定菜就立刻失败，而是订单满意度不足且无剩余补救机会时失败 |

不做自动连锁，是为了确保每一单位食材都来自玩家主动选择，避免传统三消中“莫名其妙掉进一堆东西”的失控感。

### 3.3 长连与特殊效果

| 单次连线长度 | 效果 |
| --- | --- |
| 3～4 | 普通投料 |
| 5～6 | 获得“细切”标签，提高本锅质量分 |
| 7～9 | 获得“鲜香”标签，并在棋盘生成 1 个调味星 |
| 10+ | 触发“灵感长连”，获得稀有配方所需的灵感标签 |

特殊效果不凭空变出菜；它只增加技巧标签、调味机会或质量分。稀有菜仍需满足食材和锅具条件。

### 3.4 首章关卡结构

- 普通订单：做出已知菜；
- 研究订单：根据口味/食材提示发现未知菜；
- 双拼订单：连续完成两道菜；
- 限制订单：禁用某类食材或限制投料次数；
- 星级目标：完成订单只是 1 星，比例、长连和剩余补救次数决定 2～3 星。

首章不做：实时倒计时、Boss、障碍物海、复杂人物技能、多个烹饪小游戏。

### 3.5 局长目标

- 新手订单：45～75 秒；
- 标准订单：90～150 秒；
- 双菜/研究订单：不超过 180 秒；
- 第一次新菜揭晓动画不可跳过，重复揭晓可点击加速。

## 4. 消除方式选型

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 传统交换三消 | 用户最熟悉，关卡工具成熟 | 自动连锁导致投料失控，数量与菜品关系弱，极易成为换皮 | 不选 |
| 点击成团消除 | 操作直接、开发快 | 对数量控制一般，重复感强，组合空间有限 | 备选 |
| 三槽式点选消除 | 变现成熟、关卡易卡点 | 与“真实下锅”关联弱，容易像羊了个羊换皮 | 不选 |
| 合成升级 | 收集与长线成熟 | 单局较长，盘面管理压过开锅惊喜 | 可做未来支线，不做核心 |
| **同类连线采集** | 数量可控、手感直观、无随机连锁、适合竖屏单手 | 需要靠配方、订单与特殊长连避免单调 | **推荐** |

关键决策：项目可以继续对外使用“消消”，但内部玩法定义应为“连线采集消除”，不要强行追求传统三消标签。

## 5. 食材如何影响料理结果

### 5.1 食材数据模型

每种食材至少包含：

- 基础身份：番茄、鸡蛋、香菇等；
- 食材族：蔬菜、肉类、蛋奶、主食、水果、调味；
- 风味标签：鲜、甜、酸、辣、咸、香；
- 功能标签：主料、辅料、香料、酱汁、装饰；
- 适配锅具：炒、煮、烤、冷制等；
- 冲突标签：例如水果甜味与部分重口汤底冲突；
- 稀有度与棋盘权重；
- 图鉴熟练度任务。

### 5.2 数量与比例

数量直接使用连掉的格数，不做“3 个格子只算 1 份”的隐藏换算。

例：

- 番茄 6、鸡蛋 5、葱 2、炒锅 → 番茄炒蛋；
- 番茄 3、鸡蛋 8、葱 2、炒锅 → 葱香厚蛋烧倾向；
- 番茄 6、鸡蛋 5、葱 2、汤锅 → 番茄蛋花汤；
- 草莓 7、鱼 6、辣椒 5、汤锅 → 对应的黑暗料理，而不是随机普通菜。

配方使用范围和比例，不要求玩家精确到单格：

- 必需食材：最小/最大数量；
- 主辅比例：例如番茄占 35%～60%、鸡蛋占 25%～50%；
- 可选加分食材；
- 禁忌或冲突组合；
- 必需锅具与技巧标签。

### 5.3 投料顺序

MVP 中，顺序只作为少数隐藏配方的条件，不成为所有菜的基础要求。否则玩家需同时记种类、数量、比例、顺序和锅具，学习负担过高。

### 5.4 锅具影响

- 炒锅：突出主料、长连和爆香，适合短流程；
- 汤锅：容忍更多辅料，偏向均衡与汤品；
- 烤箱、甜品台、烧烤架、饮品机：后续章节解锁，同一食材组生成完全不同的料理族。

锅具皮肤不能改变配方判定或强度，只改变外观、火焰、入锅和揭晓特效。锅具“等级”可以提高容错、提示或基础收益，但不能让付费皮肤成为稀有菜必要条件。

## 6. 料理生成系统

### 6.1 确定性原则

**同一食材数量＋同一锅具＋同一技巧标签，必须得到同一道菜。**

随机数只用于棋盘生成、奖励表现和非关键装饰，不参与最终菜品选择。这样玩家才能研究、复现和分享配方。

### 6.2 解析顺序

1. 过滤锅具不匹配和缺少必需食材的配方；
2. 计算候选菜匹配分；
3. 满足隐藏稀有配方时优先生成稀有配方；
4. 否则选择最高匹配的普通/特色配方；
5. 没有达到阈值时生成对应锅具的“兜底料理族”；
6. 冲突分过高时生成可收藏的黑暗料理。

候选匹配分建议：

| 维度 | 权重 |
| --- | ---: |
| 必需食材覆盖 | 45 |
| 数量/比例接近度 | 25 |
| 锅具适配 | 15 |
| 可选搭配与协同 | 10 |
| 长连/灵感标签 | 5 |
| 冲突惩罚 | 0～-40 |

普通候选达到 70 分才可生成；低于阈值进入兜底或黑暗料理。具体阈值必须由枚举模拟和试玩校准，不在立项时硬编码。

### 6.3 稀有度与当次质量必须分离

料理图鉴稀有度：

- 普通：基础配方，帮助学习规则；
- 特色：需要更合理的比例或可选辅料；
- 珍稀：需要特殊长连、隐藏搭配或章节条件；
- 传说：章节级秘密配方，必须可通过游玩获得，不能付费独占；

黑暗料理不是最低稀有度，而是独立料理标签：冲突配方或实验事故会产生黑暗料理，并进入独立事故图鉴。黑暗料理本身仍可分普通、特色、珍稀，拥有各自收藏价值和幽默文案。

当次烹饪质量：1～3 星，依据配方匹配度、订单契合度、长连技巧和剩余补救机会计算。

这样可避免“同一道番茄炒蛋因为连得长就突然变成传说菜”的逻辑问题。

### 6.4 可理解性设计

- 锅边持续展示当前前三种食材及真实数量；
- 未知配方显示 1～3 条研究线索，不直接显示完整答案；
- 开火前给出“很像一道熟悉的家常菜 / 似乎缺少蛋类 / 食材有些冲突”等模糊反馈；
- 揭晓后说明关键因果：“番茄与鸡蛋比例合适＋炒锅”；
- 图鉴记录玩家已复现过的最佳配比范围，但不公布所有传说配方。

## 7. 菜谱与图鉴系统

### 7.1 菜谱图鉴

每道菜页面包含：

- 完整料理图、名称、稀有度、料理族；
- 首次发现时间、发现时锅具、最佳星级；
- 已知必需食材和玩家已验证的数量范围；
- 仍未解开的可选搭配，以剪影或研究便签表示；
- 料理小故事、收藏印章和主题套装进度；
- “去研究”按钮，直接跳转合适订单，不做网页式长列表。

### 7.2 食材图鉴

每种食材包含：

- 可爱主图、风味和食材族；
- 已发现的搭档食材；
- 适合锅具；
- 参与过的菜谱数量；
- 熟练度任务，例如累计连出 7 个番茄、用番茄发现 3 道菜。

### 7.3 收集目标

- 单道菜发现；
- 料理族套装，例如“家常三件套”；
- 同一食材的搭配研究；
- 锅具专精；
- 黑暗料理事故档案；
- 章节研究完成度。

## 8. 局外成长与长期内容

### 8.1 首版成长轴

1. **研究等级**：非消耗经验，解锁食材、菜谱线索、锅具和章节；
2. **厨房升级**：金币升级，改善提示、容错或普通收益；
3. **菜谱图鉴**：发现与星级收集；
4. **食材熟练度**：完成小目标，奖励金币、装饰或研究线索；
5. **章节星级**：推动家常厨房毕业和下一区域预告。

### 8.2 厨房升级节点

- 炉灶：提升烹饪基础收益，不改配方；
- 备菜台：提升目标食材出现的最低保障，降低坏盘；
- 研究书架：增加未知配方线索；
- 餐具柜：提高满星订单的金币奖励；
- 调味架：解锁特殊调味星；
- 展示墙：增加收藏陈列位，仅视觉成长。

### 8.3 后续章节框架

家常灶台 → 西式烤房 → 甜品工坊 → 街头烧烤 → 饮品实验台 → 节日快闪厨房。

每个章节只增加一组核心变量：新锅具/方法、新食材族、新料理模板和 1 个轻机制，避免旧系统指数膨胀。

### 8.4 首版不做

- 体力系统；
- 强制签到连续惩罚；
- 装修自由摆放；
- 角色养成；
- 公会、排行榜和实时社交；
- 云端账号与多端同步。

## 9. 经济与变现框架

### 9.1 经济原则

- 不看广告、不付费的玩家也能完成首章和发现所有核心菜谱；
- 广告解决“再试一次、少等一步、加速收益”，不制造人为问题；
- 皮肤只改变厨房、锅具、餐具、连线轨迹和揭晓效果；
- 不卖影响配方公平性的食材概率；
- MVP 先验证留存和开锅期待，再接真实广告与支付。

### 9.2 货币

首版只保留两类核心数值：

- 金币：厨房升级、普通外观解锁；
- 研究经验：非消耗，推进章节。

撤回券、洗牌券等作为直接道具，不再增加“钻石”等第三货币。外观优先直接定价，减少货币迷雾。

### 9.3 激励广告场景

按优先级分批开放：

1. 失败后增加 2～3 次采集机会，每单最多 1 次；
2. 结算金币翻倍，每日限制次数；
3. 每日研究宝箱；
4. 当局增加第 4 个临时投料位；
5. 免费洗牌或神秘食材，必须由玩家主动点击。

禁止：开局强弹、失败立刻弹、连续两个广告入口、把关闭按钮伪装成继续按钮、广告不给奖励。

### 9.4 插屏广告立场

**不进入首个可玩 MVP。**

只有在留存测试通过且玩家明确接受后，才测试：

- 仅在完成若干订单、返回厨房的自然断点出现；
- 首次游戏前 20 分钟不出现；
- 初始频控不高于每 12 分钟 1 次、每日不高于 3 次；
- 失败后、揭晓新菜前后、支付后不出现；
- 一旦 TapTap 评价集中反感，直接关闭，而不是调小关闭按钮。

### 9.5 内购

候选商品与价格只作测试锚点，不在立项冻结最终价格：

- ¥12～18：研究员支持包，永久免自动插屏＋专属锅具皮肤；
- ¥6～12：单个厨房/餐具/连线效果外观；
- ¥18～30：完整主题厨房套装；
- 主题通行证：只在有稳定月度内容生产能力后开放，不进入 MVP。

TapTap 内购目前支持消耗型和非消耗型商品；官方最佳实践推荐用服务端确认履约并接收退款 Webhook。真实内购因此应与最小后端一同进入后续商业化阶段，不能用纯客户端永久标记冒险上线。

### 9.6 首章数值框架

- 20 个订单预计产出约 5,500 金币；
- 首章 6 个关键升级节点总成本约 4,800 金币；
- 无广告玩家正常完成首章可购买约 80%～90% 的功能升级；
- 广告只把进度加快约 15%～25%，不应变成唯一可行路线；
- 失败增加步数只补救当前订单，不永久提高难度。

数值必须用模拟器跑通后再定稿，上述仅是经济方向。

## 10. UI 信息架构

### 10.1 主导航

厨房主场景是首页，不单独制作“网页式首页”。玩家通过场景中的实体入口和底部短导航进入：

- 订单板；
- 菜谱书；
- 食材柜；
- 厨房升级；
- 商店/主题陈列。

### 10.2 12 个必须先完成视觉定义的界面/状态

| 编号 | 界面 | 游戏化构图要求 |
| --- | --- | --- |
| 1 | 厨房首页 | 暖色料理研究厨房实景，炉灶为视觉中心，订单板和图鉴书是实体热点 |
| 2 | 订单/关卡选择 | 软木订单板或传菜窗，不用纵向任务列表 |
| 3 | 开局准备 | 锅具放在灶台上，增益道具像备菜盘，不做勾选表单 |
| 4 | 消除对局 | 顶部订单、中央棋盘、下方真实锅具与投料槽，信息不遮挡食材 |
| 5 | 食材入锅 | 食材从原格沿弧线飞入锅，锅中颜色/体积/计数同步变化 |
| 6 | 烹饪完成 | 锅盖、火焰、蒸汽和厨具动作形成短演出，非加载条 |
| 7 | 料理揭晓 | 盘子居中、料理占主要面积，稀有度决定灯光、构图和音效 |
| 8 | 菜谱图鉴 | 一本可翻页的研究菜谱，分类用书签，不用后台表格 |
| 9 | 食材图鉴 | 食材抽屉/标本柜式陈列，点开看搭档与熟练度 |
| 10 | 厨房升级 | 直接在厨房场景中高亮可升级物件，升级前后有视觉变化 |
| 11 | 商店/付费 | 厨房精品陈列架＋大件预览，商品不能像电商列表堆卡片 |
| 12 | 广告奖励/主题活动 | 每日研究箱、主题料理台和奖励演出，明确标“广告” |

### 10.3 390×844 对局布局基线

| 区域 | 高度参考 | 内容 |
| --- | ---: | --- |
| 顶部安全区 | 24 px | 刘海/状态栏适配 |
| HUD | 44 px | 暂停、订单编号、剩余补救次数 |
| 订单提示 | 78 px | 目标、线索、满意度 |
| 棋盘 | 360 px | 7×7，单格约 46 px，加间距 |
| 锅与投料舞台 | 190 px | 锅、3 个投料记录、实时材料计数 |
| 道具栏 | 88 px | 撤回、洗牌、神秘食材、开火 |
| 底部安全区 | 24 px | 手势区适配 |

实际实现必须同时检查 360×800、390×844、430×932 和窄刘海机型，390×844 是验收基准，不是唯一适配尺寸。

### 10.4 UI 否决条件

出现任意一项，阶段验收不通过：

- 同屏超过 3 个同形同半径的白色圆角卡片；
- 大面积纯色/渐变背景上堆文字和按钮；
- 主要界面以左对齐列表为骨架；
- 使用浏览器、后台、表单式按钮和默认图标观感；
- 用文字名称代替料理主图、锅具、食材或奖励演出；
- 食材飞入锅后，锅中内容、计数和最终菜没有同步关系；
- 稀有度只改边框颜色，没有构图、动画和音效差异。

## 11. 美术方向与奖励表现

### 11.1 视觉主题

**暖色复古料理研究所**：家常厨房的烟火气＋手账式研究记录＋少量实验器具趣味，不做医院式白色实验室，也不做日式二次元角色餐厅。

风格关键词：

- 2D/轻 2.5D 卡通；
- 圆润、可口、轻厚涂；
- 奶油搪瓷、木质台面、铜色标签；
- 食材轮廓清楚，2～3 层明暗，不做照片写实；
- 手账贴纸、印章、便签作为研究元素。

基础色：奶油 `#FFF3D6`、番茄红 `#F2635F`、香草绿 `#65B879`、搪瓷青 `#4A9B91`、可可棕 `#5A3D32`、黄油金 `#F6C453`。

### 11.2 料理视觉优先级

1. 料理揭晓主图；
2. 食材棋盘辨识度；
3. 食材入锅和锅中层次；
4. 厨房主场景；
5. 图鉴与升级；
6. 商店和活动。

任何时候都不能先做 100 个关卡，却只有占位菜品图。

### 11.3 四档稀有度＋黑暗标签揭晓规范

| 分类 | 时长 | 构图/光效 | 音效与触感 | 收藏表现 |
| --- | ---: | --- | --- | --- |
| 普通 | 0.8s | 暖白盘、轻蒸汽、柔光落台 | 清脆落盘声 | 普通研究章 |
| 特色 | 1.2s | 青铜餐具边、3～5 个食材粒子 | 两段上扬音 | 书页亮边＋特色章 |
| 珍稀 | 1.8s | 蓝紫暗场、食材环绕、镜头轻推进 | 短旋律＋中等震动 | 图鉴自动翻页、珍稀标签 |
| 传说 | 2.6s | 剪影停顿→金色锅盖闪开→完整摆盘 | 独立主题音＋强弱两次震动 | 全屏研究认证、永久展示位 |
| 黑暗标签 | 在原稀有度演出上叠加黑烟、锅盖弹跳、歪盘但仍可爱 | 喜剧弹簧/闷响 | “研究事故”红章＋独立黑暗图鉴，仍保留自身稀有度 |

首次揭晓按完整演出，重复结果可加速。设置中必须提供减少震动、减少闪烁和跳过重复动画。

### 11.4 料理质量星级表现

质量星级叠加在稀有度演出后，不改变料理稀有度：

- 1 星：基本完成；
- 2 星：比例好、订单吻合；
- 3 星：比例优秀＋长连技巧＋高满意度。

## 12. 素材生产方案

### 12.1 混合式生产

不为每道菜制作昂贵 CG，也不全部依赖程序随机拼图。

- 棋盘食材：独立模块化图标；
- 锅内表现：食材小块、酱汁底色、蒸汽和火焰分层；
- 料理主图：用“容器底＋料理主体＋主料块＋配菜＋酱汁＋装饰＋蒸汽/高光”组合，再做人工校正；
- 传说菜：允许少量单独绘制的英雄图，但沿用同一图层规范；
- 厨房：场景底图＋可升级物件分层，不做完全自由装修。

### 12.2 MVP 素材预算

| 类型 | MVP 数量 |
| --- | ---: |
| 棋盘食材 | 10 |
| 完整料理 | 15（含 2 个黑暗、3 个稀有/传说） |
| 锅具 | 2 |
| 厨房场景 | 1 套＋6 个可升级分层物件 |
| 餐具/容器底 | 4 |
| 食物主体模板 | 6 |
| 配菜/装饰模块 | 12～16 |
| 通用特效 | 入锅、火焰、蒸汽、闪光、烟雾、金币、研究章共 7 组 |
| UI 图标 | 约 25 |
| 料理揭晓音效 | 5 套＋通用变体 |

### 12.3 规格

- 食材主源文件按 512×512 制作，实际导出按显示尺寸与图集缩放；
- 料理主图源文件建议 1024×1024，游戏内按需求导出；
- 图集原则上不超过 2048×2048，按场景和生命周期拆分；
- 所有源文件保留分层、命名、色板和导出预设；
- 字体只使用明确可商用许可，保留许可证；
- 购买素材保留订单和授权页；原创/AI 辅助素材保留源文件、提示词、过程版本和人工修改记录，以应对 TapTap 素材证明要求。

### 12.4 内容扩展模板

以后每增加一个主题，只新增：

1. 1 个料理方法/锅具；
2. 6～10 种食材；
3. 12～20 道料理；
4. 1 套厨房环境替换；
5. 2～3 组专属特效；
6. 数据表和订单，不复制玩法代码。

## 13. 技术选型

### 13.1 引擎对比

| 技术 | 适配评价 |
| --- | --- |
| **Cocos Creator 3.8.8 LTS + TypeScript** | 最适合。与你的前端/TS 背景一致，2D、动画、粒子、Prefab、Android/iOS 原生构建都够用，移动包体与开发效率平衡较好。 |
| Unity | 插件生态和原生 SDK 经验最成熟，但 C#、编辑器和项目体量更重，对此项目属于过度配置。 |
| Godot | 2D 能力好、开源，但非 TS 工作流，国内广告/TapTap 原生 SDK 接入资料和现成桥接较少。 |
| Phaser/Web + 壳 | 原型快，但 TapTap APK、原生广告、支付、合规 SDK、资源管理和设备性能链路更麻烦，不作为正式方案。 |

官方当前仍把 Creator 3.8 标为 LTS，产品下载页列出 3.8.8。项目应锁定 3.8.8，不在开发中途追逐 4.x 或随意升级小版本。

### 13.2 平台策略

- MVP：Android APK、TapTap 测试优先；
- iOS：核心留存验证后再构建；
- 首版单机离线可玩，不强制登录；
- TapTap 登录、成就、云存档按真实需求接入，不为“看起来完整”提前增加账号复杂度；
- 支付与广告通过抽象接口隔离，编辑器和测试包使用 Mock 实现。

### 13.3 推荐代码结构

- `core/board`：纯 TypeScript 棋盘、连线合法性、补盘和种子随机；
- `core/recipe`：纯 TypeScript 配方解析器、评分与冲突判定；
- `core/order`：订单目标、满意度、失败/补救；
- `data`：食材、配方、订单、升级、经济 JSON/TS 配置；
- `presentation`：Cocos 场景、Prefab、动画、音频、震动；
- `services`：存档、分析、广告、支付、隐私同意、平台桥接；
- `tools`：配方枚举模拟、内容校验、截图和回归测试；
- `tests`：棋盘、配方和经济的确定性测试。

核心逻辑不直接依赖 Cocos 节点，使配方和数值可以用 Vitest 等普通 TS 测试快速跑上千组组合。

### 13.4 数据与存档

- 所有食材、配方、订单和经济数据配置化；
- 存档为带版本号的数据结构，提供迁移函数；
- MVP 本地存档，重要 IAP 权益上线前改为服务端可恢复；
- 每个关卡记录随机种子，便于复现坏盘和配方 Bug；
- 不在用户同意隐私政策前初始化会采集设备标识的分析/广告 SDK。

### 13.5 性能基线

- 390×844 下目标 60 FPS，中低端 Android 关键演出不低于 45 FPS；
- Android 冷启动目标小于 5 秒（中端测试机）；
- MVP 安装包目标小于 150 MB；
- 避免运行时频繁创建销毁食材节点，使用对象池；
- 特效按稀有度分档，低性能模式降低粒子和后处理；
- 至少覆盖 360×800、390×844、430×932 和安全区机型。

### 13.6 TapTap 接入风险

TapTap Android SDK 提供原生 Gradle 接入，官方 IAP 也以 Android/Unity 为主要示例，没有把 Cocos 列为一等接入路径。因此 Cocos 正式方案应预留 Java/Kotlin 原生桥接层。进入商业化前必须做一个独立技术尖刺：登录/支付/广告回调、切后台恢复、旋转锁定、隐私同意与失败重试。

## 14. 第一版 MVP 范围

### 14.1 内容范围

- 1 个“家常灶台”厨房；
- 7×7 连线采集棋盘；
- 10 种食材；
- 2 个锅具：炒锅、汤锅；
- 15 道可收藏料理：8 普通、4 特色、2 珍稀、1 传说；其中 2 道带黑暗料理标签；
- 20 个订单：8 教学/已知、6 研究、4 限制、2 双菜；
- 菜谱图鉴、食材图鉴；
- 6 个厨房升级节点；
- 金币、研究经验、1～3 星；
- 撤回、洗牌、神秘食材 3 种道具的可用版本；
- 广告/支付只保留接口和 Mock，首个内部 MVP 不接真实变现 SDK；
- 本地存档、基础设置、音效/震动/减少动画。

### 14.2 MVP 不包含

- 第二厨房、人物剧情、自由装修；
- 体力、签到、通行证、排行榜；
- 真实支付、真实自动插屏；
- 服务器、云存档、社交；
- 大量障碍物与 100+ 关卡；
- iOS 正式包。

### 14.3 MVP 成功标准

内部/小规模试玩至少满足：

- 80% 首次玩家能在简短教学后解释“食材为何变成这道菜”；
- 70% 玩家无需提示完成第一道指定菜；
- 60% 玩家在完成首单后主动再玩一单以尝试新料理；
- 新料理揭晓满意度平均不低于 4/5；
- 少于 20% 玩家反馈“结果太随机/不知道为什么”；
- 20 个订单不存在不可解种子、存档损坏或阻塞流程；
- 390×844 实机/真实运行截图达到 UI 验收，不是网页卡片观感。

若“主动再玩一单”低于 40%，优先重做开锅期待和配方反馈，不扩内容。

## 15. 完整开发阶段与强制闸门

### 总规则

- 每一阶段只向 Codex 下发该阶段任务书；
- Codex 必须列出实际修改文件、测试结果、未完成项；
- 每阶段都必须提交 390×844 **真实运行截图**，不能用设计稿冒充；
- 从阶段 G1 开始，截图至少包括正常态、关键反馈态和异常/空态；
- 用户明确回复“本阶段通过”后，才能下发下一阶段；
- UI 不合格时只修 UI，不以“先完成功能”进入下一阶段。

### G0：立项基线（当前阶段）

**目标**：冻结产品假设、玩法方向、MVP、技术和风险。

**功能范围**：无代码；完成本文档与关键分歧确认。

**不做**：项目脚手架、素材生成、游戏逻辑、广告 SDK。

**给 Codex 的当前任务书**：无。本阶段禁止开发。

## 16. 最大风险与验证方法

| 风险 | 早期信号 | 验证/应对 |
| --- | --- | --- |
| 仍像食材换皮消除 | 玩家只谈连线，不谈锅和菜 | G2 只做 6 道菜测试；询问玩家为何出这道菜、是否想换配比再试 |
| 料理结果过于随机 | “不知道为什么”“配方是猜的”超过 20% | 确定性解析、开火前线索、揭晓因果说明、坏盘保障 |
| 规则太重 | 玩家记不住数量/比例/锅具/顺序 | MVP 弱化顺序，只保留三次投料与锅具；教学只教一个变量 |
| 连线玩法单调 | 第 3 单开始操作机械 | 用订单线索、长连、锅具和配方目标变化，不急着堆障碍物 |
| 料理图不诱人 | 揭晓满意度低于 4/5 | G1 先做普通/稀有/黑暗 3 个样片，艺术不通过不写完整系统 |
| 内容组合爆炸 | 多个配方同分、兜底泛滥 | 配方优先级、数据校验、枚举工具和固定随机种子回归 |
| 广告损害 TapTap 口碑 | 评论集中出现“骗广告/强制广告” | MVP 不上插屏；激励自愿；按评论和留存远程关闭广告位 |
| 美术成本失控 | 每道菜都需从零画整张图 | 分层模块＋人工校正，传说菜才使用少量英雄图 |
| 素材权属不清 | 无源文件、授权或生成记录 | 从第一天维护素材台账、分层源文件、许可证和购买凭证 |
| Cocos 原生 SDK 接入拖延 | 支付/广告回调在 Android 工程不稳定 | G5 前独立原生桥接尖刺，核心逻辑不依赖 SDK |
| TapTap 资质阻塞 | 做完游戏才发现无法商业化下载 | G1 同期确认主体、软著、版号或合作发行路线 |
| 范围膨胀 | MVP 前出现第二章、角色、活动 | 阶段闸门；未通过不得下发下一阶段任务 |

### 16.1 最关键的三个验证实验

**实验 A：因果与期待**

- 5～10 名目标玩家；
- 只提供 6 食材、6 配方和 3 单；
- 观察是否主动看锅、是否能预测、是否愿意改变配比重试；
- 不问“好不好玩”，问“为什么出了这道菜”和“下一锅你想怎么改”。

**实验 B：美术奖励**

- 同一料理做普通、稀有、传说、黑暗四套揭晓；
- 测试是否一眼分级、是否愿意截图、动画是否过长；
- 若只靠边框颜色才分得出，判定失败。

**实验 C：配方枚举**

- 用工具枚举食材数量、锅具与技巧标签；
- 检查同分候选、永远触发不了的配方、过度常见的黑暗料理；
- 在生产内容前先让解析器可解释、可重复、可覆盖测试。

## 17. TapTap 发布前置事项

### 17.1 资质

TapTap 当前审核细则明确：大陆移动游戏开放下载需要资质齐全；没有版号的游戏不得在大陆地区设置任何形式的内购计费，预约和信息展示可先进行。还需要关注软著、主体、授权链、素材证明、包名、正式签名和版本号。

因此必须尽快选择其中一条路线：

1. 自有合规主体＋软著＋版号/发行能力；
2. 与已有资质的发行方合作；
3. 先做内部/受限测试和 TapTap 预约页，商业化与正式下载等资质解决后再开；
4. 如转海外 TapTap/其他平台，另行评估地区支付、隐私和商店规则。

这属于发行路线问题，不阻塞 G1/G2 玩法和视觉验证，但必须在 G3 前形成明确方案。

### 17.2 商店与广告规则

- 广告不可伪装系统通知或诱导点击；
- 不得有无法关闭的悬浮/弹窗广告；
- 广告与内容混合时必须显著标注“广告”；
- 商店截图和视频必须清晰、与游戏实际一致；
- 游戏名、App 名和资质信息需要一致；
- 商业素材、购买素材和原创素材需保留授权/原创证明。
